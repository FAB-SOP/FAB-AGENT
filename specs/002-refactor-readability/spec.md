# Feature Specification: 동작을 보존하는 코드 가독성 리팩터링

**Feature Branch**: `feat/architecture`

**Created**: 2026-10-21

**Status**: Draft

**Input**: User description: "전체 프로젝트의 구조를 파악해. 이후 각 파일들이 어떻게 실행되는지 확인하고 기능이 바뀌지 않는 선에서 코드의 가독성이 좋아지도록 바꿀거야."

## 개요

FAB CONTEXT는 화면(프론트엔드), 업무 시스템(Spring backend), AI 조사 보조자(Agent Worker · 업무/지식 MCP)로
구성된다. 짧은 기간에 여러 사람이 만든 코드라 읽기 어려운 곳이 많다. 이 기능은 **사용자가 보는 동작은 그대로 둔 채**
코드를 읽고 고치기 쉽게 바꾸는 작업이다. 기준은 헌법 원칙 VIII(동작을 보존하는 리팩터링 · 읽기 쉬운 코드)이다.

**현재 상태 (2026-10-21, 기준 커밋 `ee171d2` 측정)**

| 구성요소 | 규모 | 확인된 가독성 문제 |
|---|---|---|
| 화면 | 24개 파일 · 613줄 | 여러 컴포넌트 · 함수가 한 줄에 압축됨 — 한 줄 최대 2,711자, 1,000자 넘는 줄이 있는 파일 7개, 160자 넘는 줄이 있는 파일 22개 |
| AI 조사 보조자 · 도구 서버 | 51개 파일 · 3,402줄 | 40줄 넘는 함수 11개(최대 143줄) |
| 업무 시스템 | 153개 파일 · 10,887줄 | 40줄 넘는 메서드 9개(최대 66줄) — 대시보드 집계 · 승인 결정 · 회신 · 시계열 · 시드 · 증거 계산 등 |
| 평가 · 데이터 조립 · 점검 스크립트 | 11개 파일 · 1,229줄 | 40줄 넘는 함수 2개 |
| 조사 보조자 · 스크립트 공통 | — | 뜻을 알 수 없는 한두 글자 이름 432곳(`r` 97 · `c` 45 · `x` 39 · `p` 29 · `f` 23 …) |

**행위자**

| 행위자 | 이 기능에서의 관심 |
|---|---|
| 팀 개발자 | 처음 보는 파일도 빠르게 이해하고 안전하게 고칠 수 있어야 한다 |
| 코드 리뷰어 | 리팩터링이 동작을 바꾸지 않았음을 근거로 확인할 수 있어야 한다 |
| 서비스 사용자(엔지니어 · 정비팀 · 관리자) | 아무 차이도 느끼지 않아야 한다 |

## Clarifications

### Session 2026-10-21

- Q: 이번 리팩터링 범위는? → A: 현재 구현된 코드 기준으로만 진행한다 — 기준 커밋 `ee171d2`에 있는 실행 코드 전체(US1–US5)가 대상이며, 새 기능 · 새 모듈 · 새 테스트는 추가하지 않고 기존 코드의 구조 · 이름만 정리한다.
- Q: 압축된 화면 코드를 어떻게 펼치나 — 개발용 정리 도구 예외 허용? → A: 도구 없이 손으로 펼친다. 새 의존성 금지(FR-006)를 예외 없이 지킨다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 동작 기준선 확보와 동작 불변 확인 (Priority: P1)

리뷰어는 리팩터링을 시작하기 전에 현재 동작의 기준선(모든 자동 테스트 결과, 공개 API 계약 대조 결과, 전체 업무 흐름
점검 결과)을 기록해 둔다. 각 리팩터링 단계가 끝날 때마다 같은 점검을 다시 돌려 기준선과 같은지 비교하고, 하나라도
다르면 그 단계를 되돌린다.

**Why this priority**: 이것이 없으면 "기능이 바뀌지 않았다"를 증명할 수 없다. 다른 모든 이야기의 전제다.

**Independent Test**: 코드를 하나도 바꾸지 않은 상태에서 기준선을 두 번 만들어 결과가 같은지(재현성) 확인한다.

**Acceptance Scenarios**:

1. **Given** 리팩터링 전 코드, **When** 기준선 점검을 실행하면, **Then** 테스트 통과 · 건너뜀 수, 계약 대조 결과,
   업무 흐름 점검 결과가 날짜와 함께 기록된다.
2. **Given** 리팩터링 한 단계를 마친 코드, **When** 같은 점검을 실행하면, **Then** 모든 결과가 기준선과 같다.
3. **Given** 어떤 단계에서 결과가 기준선과 다르면, **When** 리뷰어가 확인하면, **Then** 그 단계는 되돌리거나 원인을
   고친 뒤에만 다음 단계로 넘어간다.
4. **Given** 리팩터링 전체, **When** 테스트 기대값을 비교하면, **Then** 기존 테스트의 기대값은 하나도 바뀌지 않았다.

---

### User Story 2 - 화면 코드를 읽을 수 있는 구조로 펼치기 (Priority: P1)

개발자가 화면 코드 파일을 열면, 한 줄에 압축된 수천 자 대신 컴포넌트 · 함수 · 화면 요소가 한 단위씩 나뉘어 있어
위에서 아래로 읽을 수 있다. 큰 화면 컴포넌트는 역할별 하위 컴포넌트로 나뉘어 있다.

**Why this priority**: 가장 읽기 어려운 곳이다. 지금은 한 줄 수정에도 줄 전체를 비교해야 해서 리뷰 · 충돌 해결이 어렵다.

**Independent Test**: 화면 코드만 바꾼 뒤 화면 자동 테스트와 빌드가 기준선과 같고, 주요 화면(로그인 · 대시보드 · 사건
상세 · 승인 · 요청 · 보고서)을 열었을 때 이전과 같게 보이고 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 압축된 화면 파일, **When** 리팩터링 후 열면, **Then** 한 줄이 정해진 길이를 넘지 않고 한 줄에 하나의
   요소 · 문장만 있다.
2. **Given** 여러 화면을 한 파일에 담은 큰 컴포넌트, **When** 리팩터링하면, **Then** 화면 · 패널 단위로 분리되어
   각 파일이 한 가지 화면 책임만 갖는다.
3. **Given** 리팩터링된 화면, **When** 사용자가 같은 조작(로그인 → 사건 열기 → 질문 → 승인 → 회신 → 보고서)을 하면,
   **Then** 화면에 보이는 문구 · 순서 · 결과가 리팩터링 전과 같다.

---

### User Story 3 - AI 조사 보조자 · 도구 서버의 긴 함수 분리와 이름 정리 (Priority: P2)

개발자가 조사 보조자의 그래프 단계, 규칙 모델, 도구 서버 등록 코드를 열면, 각 함수가 한 가지 일(조회 · 판단 · 변환 ·
저장 중 하나)만 하고, 변수 이름만 보고 무엇을 담는지 알 수 있다.

**Why this priority**: 승인 · 근거 검사 같은 핵심 규칙이 들어 있는 곳이라 이해 비용을 줄이는 효과가 크지만, 동작
보존 위험도 높아 기준선(US1) 위에서 진행한다.

**Independent Test**: 이 영역만 바꾼 뒤 조사 보조자 자동 테스트, 결정적 판단 평가(시연 사건 3건), 전체 업무 흐름
점검, 작업자 재시작 점검이 기준선과 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 40줄이 넘는 함수, **When** 리팩터링하면, **Then** 단계별 이름을 가진 작은 함수로 나뉘거나, 나누지 않은
   이유가 기록된다.
2. **Given** 한두 글자 변수 이름, **When** 리팩터링하면, **Then** 담는 값의 의미를 드러내는 이름으로 바뀐다
   (짧은 반복 인덱스 · 언어 관용 이름은 예외).
3. **Given** 외부와 약속된 이름(도구 이름 · 이벤트 종류 · 그래프 단계 이름 · 설정 이름), **When** 리팩터링하면,
   **Then** 그 이름은 바뀌지 않는다.
4. **Given** 승인 대기 중인 조사가 저장된 상태, **When** 리팩터링된 작업자로 재시작하면, **Then** 같은 지점에서 재개된다.

---

### User Story 4 - 업무 시스템의 긴 메서드 분리 (Priority: P2)

개발자가 대시보드 집계, 승인 결정, 회신 처리, 시계열 조회, 증거 계산, 시드 코드를 열면, 검증 · 조회 · 계산 · 저장 ·
응답 변환이 각각 이름 붙은 단계로 나뉘어 있어 흐름을 한눈에 볼 수 있다.

**Why this priority**: 업무 시스템은 상대적으로 정돈되어 있어 긴 메서드 몇 곳만 손보면 된다.

**Independent Test**: 이 영역만 바꾼 뒤 업무 시스템 자동 테스트, 계약 대조, 패키지 의존 점검, 업무 흐름 점검이
기준선과 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 40줄이 넘는 메서드, **When** 리팩터링하면, **Then** 단계별 메서드로 나뉘고 원래 메서드는 단계 호출의
   순서만 보여 준다.
2. **Given** 리팩터링된 업무 시스템, **When** 공개 · 내부 API 계약을 대조하면, **Then** 기준선과 차이가 없다.
3. **Given** 리팩터링된 업무 시스템, **When** 패키지 의존을 점검하면, **Then** 순환이 없고 의존 방향 규칙이 그대로다.

---

### User Story 5 - 평가 · 데이터 조립 · 점검 스크립트 정리 (Priority: P3)

개발자가 평가 · 데이터 조립 · 계약 대조 스크립트를 열면, 같은 기준(함수 길이 · 이름)으로 정리되어 있다.

**Why this priority**: 서비스 동작에는 영향이 없고 사용 빈도가 낮다.

**Independent Test**: 데이터 조립 스크립트를 다시 실행해 결과 파일이 바이트 단위로 같은지, 점검 스크립트 출력이
같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 리팩터링된 데이터 조립 스크립트, **When** 같은 입력으로 실행하면, **Then** 결과 데이터 팩이 리팩터링 전과
   바이트 단위로 같다.
2. **Given** 리팩터링된 점검 스크립트, **When** 같은 대상으로 실행하면, **Then** 출력이 리팩터링 전과 같다.

---

### Edge Cases

- 리팩터링 중 기존 테스트가 실패하면? → 테스트를 고치지 않고 코드를 되돌리거나 원인을 고친다(기대값 변경 금지).
- 이름을 바꾸려는 대상이 외부 약속(응답 필드 · 이벤트 종류 · 도구 이름 · 설정 이름 · 저장된 단계 이름)이면? → 바꾸지 않는다.
- 함수를 나누면 오히려 읽기 어려워지는 경우(예: 짧은 분기가 많은 단순 매핑, 도구 등록 목록)는? → 40줄을 넘어도
  남길 수 있지만 이유를 기록한다.
- 손으로 펼치다가 괄호 · 조건식이 어긋나 동작이 바뀌면? → 파일 단위로 펼친 직후 화면 테스트 · 빌드를 돌려 확인하고,
  펼치기와 컴포넌트 분리는 별도 단계로 나눠 어느 단계에서 바뀌었는지 추적한다.
- 리팩터링하다가 버그를 발견하면? → 이번 작업에서 고치지 않고 별도 항목으로 기록한다(동작 변경은 이 기능의 범위 밖).
- 자동 테스트가 덮지 않는 화면 동작은? → 리팩터링 전후 같은 조작을 사람이 따라가 비교한다.
- 실제 언어 모델을 쓰는 판단은 매번 결과가 달라질 수 있다 → 동작 비교는 결정적 모드(규칙 모델)로 한다.

## Requirements *(mandatory)*

### Functional Requirements

**동작 보존**

- **FR-001**: 리팩터링 전에 기준 커밋(`ee171d2`)에서 동작 기준선(자동 테스트 결과 · 계약 대조 결과 · 업무 흐름 점검 ·
  결정적 판단 평가 · 작업자 재시작 점검)을 기록해야 한다.
- **FR-002**: 각 리팩터링 단계 후 기준선과 같은 점검을 다시 실행하고, 결과가 기준선과 같아야 다음 단계로 넘어간다.
- **FR-003**: 기존 테스트의 기대값을 바꾸어서는 안 된다. 테스트 코드 자체의 정리는 기대값을 바꾸지 않는 범위에서만 한다.
- **FR-004**: 외부와 약속되었거나 저장된 이름(공개 · 내부 응답 필드, 요청 경로, 이벤트 종류, 도구 이름, 설정 이름,
  저장된 그래프 단계 이름, 저장소 열 이름)은 바꾸어서는 안 된다.
- **FR-005**: 리팩터링 중 발견한 버그나 동작 개선 아이디어는 고치지 않고 별도 목록에 기록해야 한다.
- **FR-006**: 리팩터링은 새 외부 의존성을 추가하지 않아야 한다.
- **FR-006a**: 리팩터링 대상은 현재 구현된 코드뿐이다. 새 기능 · 새 화면 · 새 API · 새 테스트를 추가하지 않는다.

**가독성**

- **FR-007**: 화면 코드는 한 줄에 하나의 요소 · 문장만 두고, 한 줄 길이가 160자를 넘지 않아야 한다. 정리 도구를
  새로 들이지 않고 사람이 직접 펼치며, 들여쓰기 · 따옴표 · 세미콜론 같은 표기는 저장소의 다른 화면 파일 중
  이미 펼쳐져 있는 파일의 방식을 따른다.
- **FR-008**: 여러 화면 · 패널을 담은 큰 화면 파일은 화면 · 패널 단위로 나누어야 한다.
- **FR-009**: 본문이 40줄을 넘는 함수 · 메서드는 단계별 함수로 나누어야 한다. 나누지 않을 때는 이유를 기록한다.
- **FR-010**: 한 함수 · 메서드는 검증 · 조회 · 계산 · 저장 · 응답 변환 중 한 가지 책임만 가져야 한다. 여러 단계를
  이어 주는 함수는 단계 호출 순서만 보여 준다.
- **FR-011**: 담는 값의 의미를 알 수 없는 한두 글자 이름은 의미를 드러내는 이름으로 바꾸어야 한다. 짧은 반복 인덱스와
  언어 관용 이름은 예외로 한다.
- **FR-012**: 분리 후에도 구성요소 간 의존 방향 규칙과 순환 금지를 지켜야 한다.
- **FR-013**: 각 구성요소의 기존 표기 관례(주석 언어 · 밀도, 이름 짓는 방식)를 따라야 한다.

**진행 · 기록**

- **FR-014**: 리팩터링은 구성요소 단위로 나누어 진행하고, 단계마다 무엇을 왜 바꾸었는지 기록해야 한다.
- **FR-015**: 리팩터링 전후의 가독성 지표(긴 함수 수, 가장 긴 줄, 의미 없는 짧은 이름 수)를 기록해야 한다.

### Key Entities

- **동작 기준선**: 리팩터링 전 점검 결과의 묶음 — 구성요소별 테스트 통과 · 건너뜀 수, 계약 대조 결과, 업무 흐름 점검,
  결정적 판단 평가, 재시작 점검, 측정 날짜.
- **리팩터링 단계**: 한 구성요소의 한 묶음 변경 — 대상 파일, 변경 이유, 단계 후 점검 결과.
- **가독성 지표**: 긴 함수 수 · 가장 긴 함수 길이 · 가장 긴 줄 길이 · 의미 없는 짧은 이름 수.
- **보류 목록**: 리팩터링 중 발견했지만 고치지 않은 버그 · 개선 아이디어.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 리팩터링 후 모든 자동 테스트의 통과 · 건너뜀 수가 기준선과 같고 실패는 0건이다.
- **SC-002**: 공개 · 내부 API 계약 대조 결과가 기준선과 같다(새 차이 0건).
- **SC-003**: 전체 업무 흐름 점검(질문 → 제안 → 승인 → 실행 → 회신 → 보고서)과 작업자 재시작 점검이 실패 0건이다.
- **SC-004**: 시연 사건 3건의 결정적 판단 결과가 기준선과 같다.
- **SC-005**: 기존 테스트의 기대값 변경이 0건이다.
- **SC-006**: 화면 코드에서 가장 긴 줄이 2,711자에서 160자 이하가 된다(160자 넘는 줄이 있는 파일 22개 → 0개).
- **SC-007**: 본문이 40줄을 넘는 함수 · 메서드가 22개(조사 보조자 · 도구 서버 11 · 업무 시스템 9 · 스크립트 2)에서
  0개가 되거나, 남은 것마다 남긴 이유가 기록된다.
- **SC-008**: 의미 없는 한두 글자 이름(허용 예외 제외)이 432곳에서 0곳이 된다.
- **SC-009**: 처음 보는 팀원이 리팩터링된 함수 하나를 골라 그 함수가 하는 일을 이름과 단계 호출만 보고 한 문장으로
  설명할 수 있다(무작위 함수 10개 중 9개 이상).

## Assumptions

- 대상은 기준 커밋 `ee171d2`에 있는 실행 코드 전체(화면 · 업무 시스템 · 조사 보조자 · 도구 서버 · 평가 · 데이터 조립 ·
  점검 스크립트)이다. 저장소에 없는 평가자 전용 정답 · 원문 파일은 대상이 아니다. 새 기능 · 새 모듈 · 새 테스트는
  추가하지 않는다(함수 분리로 생기는 같은 파일 · 같은 구성요소 안의 보조 함수 · 하위 컴포넌트는 허용).
- 테스트 코드는 기대값을 바꾸지 않는 범위의 이름 정리만 허용하고, 적극적인 리팩터링 대상에서는 뺀다.
- 동작 비교는 외부 모델 없이 결정적으로 돌아가는 모드에서 한다.
- 40줄 · 160자는 헌법 원칙 VIII과 일반적인 코드 리뷰 관행에 맞춘 기준값이다.
- 리팩터링 중 다른 팀원이 같은 파일을 고치면 구성요소 단위로 나누어 충돌을 줄인다. 진행 중 새로 들어온 기능
  커밋은 그 시점의 동작을 새 기준선으로 삼는다.
- 화면 리팩터링 결과의 겉모습 비교는 사람이 주요 화면을 따라가며 확인한다(화면 캡처 비교 도구는 범위 밖).
