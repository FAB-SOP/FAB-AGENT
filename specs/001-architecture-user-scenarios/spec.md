## 서비스 개요

FAB CONTEXT는 반도체 공정(CVD → ETCH → CMP)에서 관리한계 이탈 같은 이상이 생겼을 때, AI 조사
보조자가 공정 데이터와 문서 근거로 원인 후보를 정리하고, 다른 공정 담당자나 설비정비팀에게 보낼
확인 요청을 **제안**하며, 담당자가 **승인한 뒤에만** 요청이 실제로 전달되는 조사 · 협업 서비스다.
모든 운전 데이터는 시연용 합성 데이터다.

**행위자**

| 행위자 | 설명 | 시연 계정 |
|---|---|---|
| 사건 담당 엔지니어 | 자기 공정의 이상 사건을 조사하고 질문 · 승인 · 조치 · 보고서를 책임진다 | `cmp.park` (CMP) |
| 앞 공정 담당자 | 다른 공정의 엔지니어. 자신에게 배정된 확인 요청만 보고 회신한다 | `etch.lee` (ETCH), `cvd.kim` (CVD) |
| 설비정비팀 | 정비 요청을 받아 점검하고 회신한다. 사건 운영 권한은 없다 | `mnt.jung` |
| 운영 관리자 | 전 공정 사건을 보고 보류 · 종료 같은 상태 전이를 한다 | `manager.choi` |
| 이상 탐지 서비스 | 관리한계 이탈을 감지해 이벤트를 보낸다(사람 아님) | 서비스 토큰 |
| AI 조사 보조자 | 근거를 모아 결과 · 제안 · 보고서 초안을 만든다. 스스로 변경을 실행하지 않는다 | — |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이상 사건 자동 접수와 기본 분석 확인 (Priority: P1)

CMP 공정 엔지니어는 출근 후 대시보드에서 새 이상 사건(예: EV-1009, CMP 후 두께가 관리 상한 위,
규격 안)을 확인한다. 사건은 탐지 이벤트로 이미 생성되어 있고 기본 분석이 자동으로 진행되어 있다.
엔지니어는 사건 상세에서 웨이퍼의 실제 공정 경로(CVD-PM1 → ETCH-PM2 → CMP-PM3), 위치별 계측,
공정별 제거량, 정상 변동 대비 편차, 그리고 AI가 정리한 **관측 사실 · 원인 후보(지지 · 반대 근거) · 한계**를
본다. 분석이 진행되는 동안 화면은 진행 상태를 실시간으로 갱신한다.

**Why this priority**: 서비스의 출발점이다. 이것만으로도 엔지니어가 데이터를 직접 모으는 시간을
줄이고, 원인을 확정하지 않는 근거 기반 첫 판단을 제공한다.

**Independent Test**: 이상 이벤트 하나를 보낸 뒤 담당 엔지니어로 로그인해 사건 목록 → 상세에서 기본
분석 결과가 사실 · 후보 · 한계로 나뉘어 표시되고 모든 항목에 근거 ID가 붙는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 탐지 서비스가 관리한계 이탈 이벤트를 보냈을 때, **When** 시스템이 이벤트를 받으면,
   **Then** 사건이 즉시 생성되고 기본 분석이 대기열에 들어간다.
2. **Given** 같은 이벤트 ID가 다시 들어왔을 때, **When** 시스템이 받으면, **Then** 새 사건을 만들지 않고
   기존 사건을 돌려준다.
3. **Given** 기본 분석이 끝났을 때, **When** 엔지니어가 사건 상세를 열면, **Then** 결과는 관측 사실 · 원인
   후보 · 한계로 나뉘고, 각 항목에는 근거 ID가 있으며, 확률 표현과 원인 확정 표현이 없다.
4. **Given** 엔지니어가 사건 화면을 열어 둔 상태에서, **When** 분석 상태가 바뀌면, **Then** 화면이 새로
   고침 없이 갱신되고, 연결이 끊기면 다시 조회해 상태를 복구한다.
5. **Given** 분석 시점 이후에 공개된 계측이 있을 때, **When** 분석이 수행되면, **Then** 그 계측은 결과에
   쓰이지 않는다.

### User Story 2 - 추가 질문, 앞 공정 확인 요청 제안과 승인 (Priority: P1)

엔지니어는 "두께 상승이 앞 공정 영향인가?"라고 질문한다. AI는 심층 조사로 ETCH 제거량이 같은 설비
정상 run 대비 크게 벗어났고(z ≈ −2.7) ETCH-PM2에 최근 정비 이력이 있음을 찾고, ETCH 공정 담당자에게
보낼 **확인 요청을 제안**한다. 제안에는 받는 사람이 볼 **요청 브리프**(편차 수치 · 확정되지 않은 원인
후보 · 관련 기록 · 확인해 달라는 항목)가 들어 있다. 엔지니어는 승인함에서 브리프를 그대로 검토하고
승인한다. 승인된 내용만 정확히 한 번 요청으로 전달된다. 거절하면 AI는 거절 사유를 반영해 결과를 정리한다.

**Why this priority**: 서비스의 핵심 가치인 "AI는 제안, 사람은 승인"을 보여 주는 흐름이며, 공정 간
협업의 시작점이다.

**Independent Test**: 시연 사건에 질문을 남긴 뒤 승인 대기 상태가 되는지, 승인 전에는 요청이 0건인지,
승인 후 요청이 정확히 1건 생기고 내용이 승인 화면의 브리프와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기본 분석이 끝난 사건에서, **When** 엔지니어가 질문을 남기면, **Then** 심층 조사가 시작되고
   근거가 앞 공정을 가리키면 그 공정 담당자에게 보낼 확인 요청이, 현재 설비 센서를 가리키면 설비정비팀
   정비 요청이 제안된다.
2. **Given** 제안이 승인 대기 중일 때, **When** 아무도 승인하지 않으면, **Then** 어떤 요청도 실제로
   만들어지지 않는다.
3. **Given** 제안을 승인할 때, **When** 제안 내용이 저장 이후 바뀌었거나 만료되었거나 다른 사람이 먼저
   결정했으면, **Then** 승인은 거부되고 다시 조회하라는 안내가 나온다.
4. **Given** 승인이 완료되면, **When** 요청이 실행되면, **Then** 승인 화면에서 본 내용과 정확히 같은 요청이
   한 번만 만들어진다(재시도해도 중복되지 않는다).
5. **Given** 제안이 질문한 본인 · 해당 공정 담당자가 아닌 사람 · 설비정비팀이 아닌 사람에게 정비 요청을
   보내려 할 때, **When** 시스템이 제안을 받으면, **Then** 제안은 저장되지 않고 이유가 기록된다.
6. **Given** 엔지니어가 제안을 거절하면, **When** 조사가 재개되면, **Then** AI는 거절 사유를 읽고 요청 없이
   결과를 정리하며 다음 질문을 받을 수 있는 상태가 된다.
7. **Given** 요청 브리프에, **When** 원인 후보가 표시되면, **Then** 모든 후보는 "확정 아님"으로 표시되고
   설비 설정값 변경 처방은 들어 있지 않다.

### User Story 3 - 다른 공정 담당자 · 설비정비팀의 요청 확인과 회신 (Priority: P1)

ETCH 담당자는 알림으로 새 확인 요청을 받는다. CMP 사건 전체 분석은 볼 권한이 없지만, 요청 브리프만으로
"어느 run의 어떤 값이 얼마나 벗어났는지, 어떤 원인을 의심하는지, 무엇을 확인해 달라는지"를 이해한다.
설비를 점검한 뒤 회신을 남기면 사건은 다시 조사 중 상태가 되고, AI는 회신 내용을 반영해 결과를 갱신한다.
설비정비팀(EV-1006 · EV-1007의 CMP 헤드 압력 · 슬러리 유량 이상)도 같은 방식으로 정비 요청을 받고 회신한다.

**Why this priority**: 공정 간 협업 루프를 닫는 단계다. 회신이 없으면 조사가 진행되지 않는다.

**Independent Test**: 앞 공정 담당자로 로그인해 받은 요청 목록 → 상세에서 브리프가 보이고 사건 분석 화면은
접근이 막히는지, 회신 후 사건 상태가 바뀌고 갱신된 분석 결과가 생기는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 승인된 확인 요청이 전달되면, **When** 받는 사람이 요청 목록을 열면, **Then** 새 요청과 그 브리프 ·
   관련 원인 후보 · 대상 설비가 보인다.
2. **Given** 받는 사람이 다른 공정 사람일 때, **When** 원 사건의 분석 결과나 원시 센서 데이터를 열려고 하면,
   **Then** 접근이 거부된다.
3. **Given** 요청이 회신 대기 중일 때, **When** 받는 사람이 회신하면, **Then** 요청은 회신 완료가 되고 사건은
   조사 중으로 돌아가며 AI 조사가 재개된다.
4. **Given** 회신이 반영된 뒤, **When** 엔지니어가 사건을 열면, **Then** 회신 내용을 반영한 새 결과가 보이고
   이전 결과는 이력으로 남는다.

### User Story 4 - 조치 · 효과 기록과 조사 보고서 확정 (Priority: P2)

엔지니어는 실제로 수행한 점검 · 정비 조치를 분석 항목(원인 후보 · 다음 확인 · 제안)과 연결해 기록하고,
이후 확인 run에서 효과를 기록한다. 조사가 정리되면 보고서 초안을 요청한다. 초안은 개요 · 조사 내용 ·
요청과 회신 · 조치와 효과 · 미해결 사항 다섯 섹션으로 만들어지고, 엔지니어가 편집해 확정한 뒤
Markdown으로 내보낸다.

**Why this priority**: 조사의 결과물을 남기는 단계로 중요하지만, 앞 단계 없이는 의미가 없다.

**Independent Test**: 조치를 기록하고 보고서 초안을 요청해 다섯 섹션이 채워지는지, 편집 · 확정 후 내용이
고정되고 내보내기가 되는지, 확정 후 변경은 새 버전으로만 되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 실제 수행한 조치를, **When** 미래 시각으로 기록하려 하면, **Then** 거부된다.
2. **Given** 효과를 기록해도, **When** 기록이 끝나면, **Then** 사건은 자동으로 종료되지 않는다.
3. **Given** 엔지니어가 보고서를 요청하면, **When** 초안이 준비되면, **Then** 다섯 섹션이 정해진 순서로 채워지고
   알림이 온다. 엔지니어가 요청하지 않으면 보고서는 만들어지지 않는다.
4. **Given** 두 사람이 같은 초안을 편집할 때, **When** 늦게 저장한 쪽의 기준 판본이 오래되었으면, **Then** 충돌로
   거부되고 다시 조회하라는 안내가 나온다.
5. **Given** 보고서가 확정되면, **When** 내용을 바꾸려 하면, **Then** 기존 판본은 그대로 보존되고 새 버전으로만
   편집할 수 있다.
6. **Given** 확인 run 결과가 없을 때, **When** 보고서가 작성되면, **Then** "해결 완료"로 표현되지 않고 미해결 · 확인 필요로 남는다.

### User Story 5 - 공정 모니터링과 참고 지식 탐색 (Priority: P3)

엔지니어는 사건이 없을 때도 담당 공정의 대시보드에서 사건 추이를 보고, 모니터링 화면에서 정상 LOT의
PM별 run · 5위치 계측 · 센서 시계열을 관리한계 · 참고 범위와 함께 본다. 참고 문서 화면에서는 실제 기술
원문 · 팀 점검 문서 · 가상 과거 사례를 검색하고, 각 문서가 공개 자료인지 가상 자료인지 구분해 본다.

**Why this priority**: 조사의 맥락을 넓혀 주는 보조 기능이다.

**Independent Test**: 담당 공정으로 로그인해 대시보드 · LOT 목록 · run 상세 · 센서 시계열 · 문서 검색이 각각
결과를 돌려주고, 다른 공정 데이터는 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 엔지니어가 담당 공정을 고르면, **When** 대시보드를 열면, **Then** 그 공정의 사건 집계가 보인다.
2. **Given** 정상 LOT의 run을 열면, **When** 센서 시계열을 요청하면, **Then** 원본 간격 그대로 결측은 결측으로
   표시되고, 정상 기준 trace가 없으면 그 이유가 표시된다.
3. **Given** 문서를 검색하면, **When** 결과가 나오면, **Then** 각 결과에 출처 구분(실제 원문 · 점검 문서 · 가상
   사례)과 버전이 표시되고, 분석 시점보다 나중의 사례는 나오지 않는다.

### User Story 6 - 관리자의 사건 상태 관리 (Priority: P3)

운영 관리자는 전 공정 사건을 보고, 외부 요인으로 기다려야 하는 사건을 보류하거나 다시 조사 중으로
돌리고, 마무리된 사건을 종료한다.

**Why this priority**: 운영상 필요하지만 핵심 조사 흐름과 독립적이다.

**Independent Test**: 관리자로 사건을 보류 → 재개 → 종료하고, 엔지니어 계정으로는 같은 전이가 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사건이 접수 · 조사 중 · 회신 대기 상태일 때, **When** 관리자가 보류하면, **Then** 보류 상태가 되고 타임라인에 남는다.
2. **Given** 보류된 사건을, **When** 관리자가 재개하면, **Then** 조사 중으로 돌아간다.
3. **Given** 엔지니어 계정이, **When** 상태 전이를 시도하면, **Then** 거부된다.

---

### Edge Cases

- AI 조사가 일시 오류 · 시간 초과로 실패하면? → 자동 재시도와 대체 모델을 거쳐, 끝내 실패하면 사건에
  실패 상태가 보이고 기본 분석을 다시 실행할 수 있다.
- 승인 대기 중에 조사 보조자가 재시작되면? → 같은 대기 지점에서 재개되어 승인 · 회신 이후 흐름이 이어진다.
- 같은 작업이 두 번 전달되면? → 한 번만 처리되고 나머지는 건너뛴다.
- 같은 쓰기 요청을 재전송하면? → 첫 응답이 그대로 재생되고, 같은 키로 다른 내용을 보내면 거부된다.
- 근거가 부족하면? → "근거 부족" 또는 "관찰"을 다음 단계로 내고 요청을 제안하지 않는다.
- 한 사건에서 제안이 반복되면? → 사건당 제안 2건 · 한 번에 하나 · 같은 담당자 · 같은 종류 반복을 막는다.
- 사용자가 설정값 처방이나 원인 확정 보고를 요구하면? → 처방 · 확정 없이 점검 후보와 한계를 설명한다.
- 검색된 문서에 실행 지시문이 들어 있으면? → 데이터로만 취급하고 권한을 늘리지 않는다.
- 실시간 알림 연결이 끊기면? → 작업 상태를 다시 조회해 복구한다.
- 외부 모델 키가 없으면? → 결정적 규칙 모델로 전체 흐름이 동작하고, 의미 검색이 설정되었는데 키가 없으면
  조용히 대체하지 않고 시작에 실패한다.

## Requirements *(mandatory)*

### Functional Requirements

**사건 · 조사**

- **FR-001**: 시스템은 이상 탐지 이벤트를 받으면 사건을 즉시 만들고 기본 분석을 시작해야 하며, 같은 이벤트 ID는
  기존 사건을 돌려줘야 한다.
- **FR-002**: 분석 결과는 관측 사실 · 원인 후보(지지 · 반대 근거 · 다음 확인) · 한계로 구분되어야 하고, 모든 사실과
  후보에는 근거 식별자가 있어야 한다.
- **FR-003**: 분석 결과는 근거 없는 확률, 원인 확정, 설비 설정값 처방을 포함해서는 안 된다.
- **FR-004**: 원인 후보는 사전에 정의된 원인 분류(15개) 안에서만 지정되어야 하고, 다음 단계(앞 공정 확인 · 현재 공정
  확인 · 관찰 · 근거 부족 · 심층 분석 필요)는 1순위 원인의 공정과 일치해야 한다.
- **FR-005**: 모든 수치 판정(관리한계 규칙 위반, 규격 이탈, 정상 분포 대비 편차, 참고 범위 이탈, 시계열 구간)은
  시스템이 계산한 값이어야 하며, AI가 쓴 수치는 조회한 값과 일치해야 한다.
- **FR-006**: 분석 시점 이후에 공개된 데이터와 과거 사례는 분석 · 검색에서 제외되어야 한다.
- **FR-007**: 사용자는 사건에 추가 질문을 남겨 심층 조사를 요청할 수 있어야 하고, 이전 질문 · 답변 · 결과 이력을
  질문 순서대로 볼 수 있어야 한다.
- **FR-008**: 사건 화면은 분석 · 승인 · 요청 · 회신 · 조치 · 보고서 상태 변화를 실시간으로 반영해야 한다.

**제안 · 승인 · 협업**

- **FR-009**: AI는 확인 요청 · 정비 요청을 제안만 할 수 있어야 하며, 사람의 승인 없이 어떤 요청 · 확정도 실행되어서는 안 된다.
- **FR-010**: 제안은 받는 사람이 볼 요청 브리프(편차 수치 · 확정 아닌 원인 후보 · 관련 기록 · 확인 항목)를 포함해야
  하고, 승인자가 본 내용과 실행 내용이 다르면 실행을 거부해야 한다.
- **FR-011**: 시스템은 제안의 받는 사람을 검증해야 한다 — 앞 공정 확인은 그 공정 담당자에게만, 정비 요청은
  설비정비팀에게만, 질문한 본인에게는 보낼 수 없다.
- **FR-012**: 승인된 변경은 정확히 한 번 실행되어야 하며, 재시도 · 중복 요청은 같은 결과를 돌려줘야 한다.
- **FR-013**: 승인 · 거절 결정은 만료 · 버전 충돌을 검사해야 하고, 거절된 경우에도 조사는 재개되어 결과가 정리되어야 한다.
- **FR-014**: 사건당 제안은 2건 이하이며, 한 번에 하나만 대기하고, 같은 담당자 · 같은 종류의 반복 제안은 막아야 한다.
- **FR-015**: 요청을 받은 사람은 자신에게 배정된 요청과 브리프만 볼 수 있어야 하며, 회신하면 조사가 재개되어야 한다.

**조치 · 보고서**

- **FR-016**: 사용자는 실제 수행한 조치(검토 · 점검 · 정비 · 기타)를 기록하고 분석 항목과 연결할 수 있어야 하며,
  미래 시각 기록은 거부되어야 한다.
- **FR-017**: 효과 기록은 사건을 자동 종료해서는 안 된다.
- **FR-018**: 보고서 초안은 사용자가 요청할 때만 만들어지고, 다섯 섹션(개요 · 조사 · 요청과 회신 · 조치와 효과 ·
  미해결)을 정해진 순서로 가져야 한다.
- **FR-019**: 보고서는 편집 · 확정 · 내보내기를 지원하고, 확정 판본은 보존되며 이후 변경은 새 버전으로만 가능해야 한다.

**권한 · 운영**

- **FR-020**: 사용자는 자신의 공정 범위에서만 사건 · 데이터를 조회하고, 사건 운영 권한이 있는 공정에서만 질문 ·
  승인 · 조치 · 보고서를 변경할 수 있어야 한다.
- **FR-021**: 사건 상태 전이(보류 · 재개 · 종료)는 관리자만 할 수 있어야 한다.
- **FR-022**: 모든 쓰기 요청은 중복 전송에 안전해야 하고, 동시 편집 충돌은 거부 후 재조회를 안내해야 한다.
- **FR-023**: 시스템은 외부 모델 없이도 전체 조사 흐름(질문 → 제안 → 승인 → 실행 → 회신 → 보고서)을 결정적으로
  수행할 수 있어야 한다.
- **FR-024**: 조사 보조자가 재시작되어도 승인 · 회신 대기 중인 조사는 같은 지점에서 재개되어야 한다.
- **FR-025**: 평가 정답 · 저작물 원문은 조사 보조자의 지침 · 검색 색인 · 실행 환경에 포함되어서는 안 된다.
- **FR-026**: 화면과 응답은 데이터가 합성 데이터이며 가상 사례가 실제 생산 사례가 아님을 표시해야 한다.

**문서 산출물**

- **FR-027**: 프로젝트는 기술 아키텍처 구조도(컴포넌트 · 기술 스택 · 런타임 배치 · 데이터 저장 · 외부 연동)와 서비스
  아키텍처 구조도(행위자 · 서비스 경계 · 서비스 책임 · 핵심 업무 흐름 · 신뢰 경계)를 제공해야 한다 —
  [architecture.md](./architecture.md). 사용자 시나리오(US1–US6)마다 시퀀스 다이어그램을 하나씩 둔다(3장). 구조도는 현재 구현을 실선으로, 미결정 · 예정 항목(메시지 큐, 서비스 간
  인증 방식, 외부 공개 배포)을 점선 · 「예정」 표시로 구분해 한 그림에 담아야 하며, 예정 항목마다 현재 상태와
  결정 대기 사유를 적어야 한다.

### Key Entities

- **사건(Incident)**: 하나의 이상 이벤트에서 시작된 조사 단위. 공정 · 웨이퍼 · run · 센서, 상태, 담당자, 타임라인, 버전.
- **작업(Job)**: 사건에 대한 AI 조사 단위 — 기본 · 심층 · 재개 · 보고서. 상태와 시도 횟수, 대기 대상(승인 · 요청).
- **분석 결과(Analysis Result)**: 관측 사실 · 원인 후보 · 다음 확인 · 한계 · 근거 · 데이터 버전. 사건별 이력.
- **제안 · 승인(Approval)**: 실행 종류(확인 요청 · 정비 요청 · 조치 기록 · 보고서 확정), 저장된 실행 내용, 내용 해시,
  만료, 결정자 · 결정, 실행 결과 참조.
- **확인 요청(Check Request)**: 종류(앞 공정 확인 · 정비), 받는 사람, 대상 공정 · 설비, 요청 브리프, 원인 후보 ID, 상태, 회신.
- **요청 브리프(Request Brief)**: 받는 사람이 판단할 수 있는 최소 맥락 — 편차 수치, 확정 아닌 원인 후보, 관련 기록, 확인 항목.
- **조치(Action)와 효과 확인(Verification)**: 실제 수행 기록, 연결된 분석 항목 스냅샷, 효과 이력.
- **보고서(Report)**: 다섯 섹션, 편집 판본, 상태(초안 · 확정), 버전.
- **공정 데이터**: 웨이퍼 경로 run, 5위치 계측, run 특징, 동결 관리한계, 센서 참고 범위, 정비 이력, 원시 시계열.
- **지식 문서**: 실제 기술 원문 조각, 팀 점검 문서, 가상 과거 사례 — 출처 구분 · 버전 · 공개 시점.
- **사용자**: 역할(엔지니어 · 관리자), 팀, 조회 공정 범위, 사건 운영 공정 범위.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 이상 이벤트 접수 후 담당 엔지니어가 사건 상세에서 첫 분석 결과를 보기까지 2분 이내다(결정적 모드 기준).
- **SC-002**: 사람의 승인 없이 실행된 요청 · 확정은 0건이다(전체 시연 흐름 점검에서).
- **SC-003**: 같은 승인에 대한 반복 실행 시도에서 실제 생성된 요청은 항상 1건이다.
- **SC-004**: 분석 결과 · 요청 브리프의 사실 · 원인 후보 중 근거 식별자가 없는 항목, 확률 표현, 설정값 처방은 0건이다.
- **SC-005**: 시연 사건 3건(EV-1006 · EV-1007 · EV-1009)에서 첫 판단(다음 단계 · 1순위 원인 · 첫 제안의 종류와 대상
  공정)이 기대 결론과 3/3 일치한다.
- **SC-006**: 요청을 받은 사람이 원 사건 분석 화면에 접근하지 않고 브리프만으로 무엇을 · 왜 확인해야 하는지 답할 수 있다
  (시연 참여자 확인 기준 100%).
- **SC-007**: 엔지니어는 질문 → 승인 → 회신 반영 → 보고서 확정까지 한 사건을 한 번의 세션에서 끝낼 수 있다.
- **SC-008**: 승인 대기 중 조사 보조자를 재시작해도 흐름 점검의 실패는 0건이다.
- **SC-009**: 다른 공정 사용자의 사건 · 데이터 접근 시도는 100% 거부된다.
- **SC-010**: 새 팀원이 구조도 문서만 보고 5분 안에 각 구성요소의 역할과 "질문에서 보고서까지" 흐름이 어떤 구성요소를
  거치는지 설명할 수 있다.

## Assumptions

- 이 기능은 새 기능 구현이 아니라 **현재 저장소에 구현된 내용을 기준으로** 구조와 사용자 시나리오를 정리하는 문서 작업이다.
  시나리오의 동작은 현재 코드 · README · 테스트 · 시드 데이터에서 확인된 것을 기준으로 했다.
- 공정은 CVD → ETCH → CMP 세 개, 공정마다 설비 3대로 한정하며, 운전 데이터는 합성 데이터 팩 v2 기준이다.
- 대표 시나리오는 시드된 시연 사건(EV-1009 주 시연, EV-1006 · EV-1007 정비 요청)을 사용한다.
- 이상 탐지 자체(관리한계 이탈 감지)는 범위 밖이며 외부 서비스가 이벤트를 보낸다고 가정한다.
- 접속 범위는 로컬 배포이며, 외부 공개용 도메인 · HTTPS · 운영 인증은 범위 밖이다.
- 서비스 간 인증 방식(현재 고정 토큰), 메시지 큐 도입 여부, 외부 공개 배포는 팀 결정 대기 중이다. 구조도는 현재
  상태를 기본으로 하고 이 항목들을 「예정」으로 겹쳐 표시한다(구현 약속이 아니라 결정 대기 표시다).
- 성공 기준의 시간 수치는 결정적(규칙 모델) 모드의 시연 환경을 기준으로 한다. 실제 모델 모드의 시간 · 토큰 · 비용
  목표는 이 기능의 범위 밖이다.
